qclone v2, as built

2026-10-13 · repo ~/proj/qrux/qclone (github.com/qrux/qclone) · describes main at 31beeef, not yet released (the Homebrew tap still serves 0.1.0) · written by the Claude Code session that built it

This covers what changed after qclone-v1-built.html (0.1.0, commit 0f0321b, documented at 1e1da38). Everything in v1 still holds unless this document says otherwise. As in v1, there was no spec: the work followed Q's requests in chat on 2026-10-13.

Read first: the new default, --order hash, works and copies correctly, but the tuner mostly fails to tune under it. On the simulated drive the demo took 141 s in hash order against 54 s in dfs order (section 6.1). A fix is proposed and awaits Q's decision. Until then, --order dfs tunes as well as 0.1.0 did.

1. What was asked

  • While running qclone, Q saw "16 readers on 1 file" and asked why not one reader on each of 16 files.
  • Q proposed ordering files by a hash of the path, to spread the reads around the drive, and agreed to keep several files in flight at once with readers taking chunks from them in turn.
  • Hash order within a window of 1,024 files (or another fast power of two), so copying can start before the walk ends.
  • A switch for DFS order, dirent order or hash order, with hash as the default. Scrambled finishing order and a few more partial files on a stopped run are acceptable.
  • The speed chart's scale must never shrink once it has grown; the rescaling "vibration" was the complaint.

3. Choices made, and why

3.1 Files in flight

  • A cap per file. If readers simply took chunks from the open files in turn, they would drift into whichever file is slow. A fast chunk frees its reader in milliseconds and a slow one holds it for seconds, so before long nearly every reader waits on the slow file. The cap, readers ÷ files, lets a slow file tie up only its share.
  • The cap lifts for the last file. It's computed from how many files are actually open, so when only one is left, it gets every reader. Without that, the end of every run would crawl.
  • Default 4, range 1 to --max-readers, in doubling steps. More files than reads in flight would leave some files idle. Moving up must gain 3%; moving down may cost up to 2%, since fewer files at once means fewer partial files on a stopped run.
  • No plausibility bound for files. Readers and chunk size can at most double throughput when doubled. A second file in flight can be a fast one beside a slow one and gain far more, so that check would wrongly void real gains.
  • With --files 1, behavior is exactly 0.1.0's (one file at a time, all readers on it).

3.2 Order

  • What hash order spreads is data age, not location. On an SSD, a path says nothing about where data physically sits; the controller spreads everything across its flash anyway. Slowness comes from the age of the data, and files in one folder were usually written together. Alphabetical order keeps the readers inside one age group; hash order mixes old and new data.
  • Key: FNV-64a of the path as displayed (relative to the destination), so the order is the same on every run, which suits resuming.
  • Window of 1,024 files, and 0.5 s patience. Q's number. Copying starts once the window fills, or once the walk has found nothing new for half a second, so a slow walk on a degraded drive never stalls the copy.
  • dfs is the old order: depth first, names sorted.
  • dirent is depth first in the file system's own listing order. On APFS that order is already a hash of the names within each folder; on exFAT it's roughly creation order.

3.3 Tuner changes for mixed workloads

  • Arms stretch. After a full round whose A arms are more than 10% off a straight line, arm length doubles, up to 16×. After a round within 3%, it shrinks by a quarter, back toward 1×. Only arms stretch; the checks for a change of region between tests keep the base length, so the tuner still notices a new region quickly.
  • Early verdicts (deciding after A C A) now need a previous full round that measured quiet, an unstretched arm length, and the two A arms within 10% (was 20%).
  • Region memory jumps only to a setting that a test in that region actually kept. Before this, it could jump to a starting value that had merely never been beaten.
  • An earlier attempt also stretched arms after every "region changed" verdict. That broke region memory on clean drives, where those verdicts are genuine region switches, so it was removed. The simulation test that caught it is TestRemembersSlowRegions.

3.4 Chart scale

  • The vertical range is the widest seen in the run, kept in the display's history, so it no longer jumps as a column in progress changes, or as wider time columns average the extremes away. The readers strip's top works the same way. An early dip widens the range for the rest of the run, which is the intended trade.

4. Where the build departs from the request

  • Default order: hash, as asked, although the tuner can't yet tune well under it (6.1).
  • Per-file cap: not part of the request. It's needed so that several files at once actually spreads the readers instead of piling them onto the slow file.

5. What was verified, and how

  • make test: 54 tests pass with the race detector, and 2 diagnostics are skipped by design. New since v1:
    • TestSlowFileDoesNotHoldEveryReader: one slow file, whose reads the drive serves one at a time, ahead of 64 fast chunks. With 1 file at once, 0 fast chunks moved during the slow file's first half; with 4, all 64 did.
    • TestOrders: dfs is sorted, hash matches the FNV order of the paths, and dirent copies everything.
    • TestWalkOrders: the walker's sorted and unsorted modes, and --order parsing.
    • TestChartScaleOnlyWidens: the axis stays put through a run whose early extremes get averaged away. It also checks that, without that history, the axis would have changed.
  • Byte-identical copies of the ~1 GB demo tree in hash order (diff -r), with nothing on stderr.
  • Demo timings on the simulated degraded drive, tuned, starting at 4 readers × 256K, 4 files: hash order 141 s, dfs order 54 s. For comparison, 0.1.0 took 52 s (dfs, 1 file at a time).
  • Pinned settings, MB/s over the first 20 s (TestDiagPinnedSettings):

6. Concerns and open issues

6.1 The tuner can't see through a shuffled mix (the main issue)

In hash order, the open files are a random mix of slow and fast ones. An arm lasts a second or two, so its bytes per second mostly reflect which files happened to be open, not the setting under test, and the swings are far larger than the effects being measured. Longer arms help only a little: most rounds still come out too noisy to decide, so tuning barely moves. The pinned measurements show hash order itself isn't slower (at 16 readers and 1 file it matched dfs). The weakness is in the measurement.

Proposed fix, awaiting Q: compare each file against itself. For each file that spans several arms (most bytes are in such files), take its own rate under the candidate setting against its rate in the A arms on either side. Combine those per-file ratios weighted by bytes, falling back to overall throughput when too few bytes are shared between arms. A file's region speed then cancels out, because it's the same file in both arms. The measure of done: make tuner-diag shows hash order tuning about as well as dfs.

6.2 Several files at once is slower in the simulator

Pinned, 4 files at once is slower than 1 in this simulator: about 30% in hash order at every reader count, and in dfs order even at 4 and 8 readers but 22% slower at 16. The simulated drive has one shared bandwidth limit for every read, the case where the drive's error correction is a single shared resource, so spreading can't gain anything, while the cap gives the slow files fewer readers. A real drive whose slowness is confined to the flash dies holding old data could behave the other way. Measuring that is the tuner's job, which depends on 6.1. A simulator variant with separate slow and fast resources would let the tests show the case where spreading wins; it hasn't been built.

6.3 Defaults to revisit once 6.1 is settled

  • --order hash as the default (Q's choice), versus dfs until the tuner copes.
  • --files 4 as the starting value, versus 1 (0.1.0's behavior).

6.4 Not yet done

  • README doesn't mention --order, --files, several files at once, or the chart scale that only widens.
  • No 0.2.0 release. make release VERSION=0.2.0 would publish it; it should wait for 6.1.
  • main is one commit ahead of GitHub (31beeef, plus this document).
  • A Status now carries up to 64 tuner decisions (was 8) so the diagnostics can print them all. The display still shows only the last.

6.5 Carried over from v1, still open

  • No run on the real degraded drive yet. Q started one. Its first observation, "16 readers on 1 file", led to this revision; no results have come back.
  • Not copied: extended attributes, ACLs, resource forks, Finder tags, hard links. No cloud remotes.
  • Copyright in AI-written code is uncertain, and every commit carries a Claude co-author line.

6.6 Environment, found during this work (not qclone's code)

Sessions working on qclone, a tool meant for external drives, should stay off /Volumes by their own discipline until Q fixes the comma.
