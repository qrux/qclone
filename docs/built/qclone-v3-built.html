qclone v3, as built

2026-10-13 · repo ~/proj/qrux/qclone (github.com/qrux/qclone) · not yet released (the Homebrew tap still serves 0.1.0) · written by the Claude Code session that built it

This covers what changed after qclone-v2-built.html (main at 31beeef, documented at 0d19ca2). Everything in v1 and v2 still holds unless this document says otherwise. As before, there was no spec: the work followed Q's requests in chat on 2026-10-13.

In one line: the A C A C A tuner is gone. qclone now keeps reads in flight = flying + min(stuck, 16), where a read is stuck after 50 ms in flight. Stuck reads are capped at 16: past that, nothing more goes to slow files. Flying reads have no fixed cap; the tuner adds them 4 at a time only while that pays, judged on reads that never got stuck. On the simulated drive the demo copy takes 46 s in hash order (v2: 141 s; 0.1.0: 52 s in dfs order).

1. What was asked

  • Q asked why the v2 tuner measured 4 → 8 readers as −10% in hash order when pinned runs showed +79% (section 6 has the answer).
  • Then Q asked for the simplest approach that works: "Don't use up too many channels. Don't go past 16 readers if they're all blocked and slow. Use more if another is fast or finishes-fast."
  • Q's clarification: "It's not hard-16. It's just saying that if 16 are stuck, then don't open more. If everything is flying, the tune automatically, and open as many as throughput increases."
  • Agreed design: reads in flight = W + min(stuck, 16). A read is stuck after 50 ms in flight. W (flying reads) starts at 4, doubles while each doubling makes it at least 5% faster, goes back when one doesn't, and every 30 s tries one step up and one down. New reads go to files with nothing stuck; slow files keep going in the stuck reads' room. Delete the tuner, files at once, the per-file cap and chunk tuning; chunks fixed at 256 KiB; the 16 becomes a flag. Done when make test passes, demo copies are byte-identical, and hash order on the simulated drive is about as fast as 0.1.0's 52 s.
  • The first cut capped flying reads at 32 (v1's cap on all reads, from SATA's 32 command slots) and gave stuck reads 16 more on top, and when there was no fresh work the idle flying slots took slow work. So a slow stretch could hold 48 reads, all stuck. Q: "Inverted. No cap on flying reads... Since the tuner will tell us if the next new reader gains us anything... What needs to get capped (especially in the SATA source case) is THE STUCK READERS." That is what was built (sections 3.2 and 3.3). Q's degraded drive is in a Thunderbolt enclosure, which, as Q pointed out, decides nothing in the design: the flying number is measured, and the stuck cap is a fixed flag.
  • The first cut also doubled the flying number. Q: "Doubling isn't always the right primitive. Just add 4 at a time." Steps are now 4 up and 4 down (3.4).

3. Choices made, and why

3.1 What counts as stuck

  • 50 ms, fixed. A healthy SSD reads 256 KiB in about a millisecond; the degraded regions take hundreds of milliseconds or seconds. A plain USB stick (8 ms per chunk at 30 MB/s) or a disk seek (10–15 ms) stays under it. It's an option in the engine (StuckAfter), not a flag.
  • Reads sent to a slow file count as stuck from the start. Otherwise each one would borrow a flying slot for its first 50 ms. With 16 slow reads of about half a second each, that's around 30 a second, so the flying reads would lose more than a slot on average.
  • A slow file is one with a stuck read, or whose last finished read took over 50 ms. When its reads come back fast again (a big file moving into a fresh region), it's a fast file again.

3.2 Where a read goes (pick)

  1. While fewer than MaxStuck are stuck, a slow file's next chunk. It counts as stuck at once, which raises the limit by one, so the flying reads keep their room.
  2. A file with nothing stuck. A file none of whose reads has finished yet gets one read at a time, so finding out that a new file is slow costs one flying read, not all of them. When no open file has a chunk to give, the next file is opened, while fewer than flying + MaxStuck files are open.

Otherwise the worker waits for fresh work. Round-robin among the files each rule accepts. The per-file cap of v2 (readers ÷ files) is gone: rule 2 keeps flying reads off slow files, and a fast file may take every flying read. With MaxStuck 0 there is no room of their own, so slow files take flying slots instead, as every read does in rclone.

3.3 Caps

  • Stuck reads: at most MaxStuck (16). Past that, nothing more goes to slow files. When everything is slow, reads in flight settle at 16, all stuck, and the flying readers wait for fresh data. A read only shows it's stuck after it was sent, so for a moment more can be stuck: flying reads that run into old data, or the first read of a newly opened file. None of those is replaced while 16 or more are stuck.
  • Flying reads: no fixed cap. The tuner adds them only while a step pays, and a drive whose queue is full gains nothing from more, so it stops there by measurement. --max-readers is an optional limit; 256, the most it ever allowed, is the backstop and the size of the worker pool's flying part.
  • Open files: at most flying + MaxStuck (20 by default). Without it, the flying reads would keep opening new files while slow ones piled up half-done, each holding two file descriptors and a part file. It also limits how often a new file's first read can land on old data.

3.4 The tuner

  • Only flying reads are measured: the engine records an op only if its read never counted as stuck, and only if it hit no unreadable sectors. Flying reads all read fresh data at about the same speed, so no noise handling is needed.
  • A measurement lasts at least 1 s and 20 flying reads. It counts ops that began after the last change and ended after the window opened (100 ms after the change). If 5 s pass without 20, the test is off ("too few flying reads") and the number holds for 10 s.
  • Climbing: add 4 while each step is at least 5% faster than the number before it, measured just before. When one isn't, go back and hold 30 s. Small steps stop within 4 of where more stops paying; doubling could overshoot by as many again (a drive whose gains end at 10 would sit at 16), and every flying read too many is one more read that can get stuck when old data turns up.
  • Rechecks every 30 s: measure the current number, try 4 more, then 4 fewer (not below 1), each against that measurement, and move only to one at least 5% faster. Equal means stay, so it never wanders on noise (a test with 10% jitter per 20 ms makes at most one change in three minutes). Up paying starts the climb again.
  • An implicit ceiling: with steps of 4 and a 5% bar, even perfect scaling stops at 80 flying reads, since 4 more is under 5% past that.
  • Starved: workers waiting for work for 100 ms, or less than 10 s of work left. Then nothing is measured; a test in progress is called off and the number goes back.
  • Removed: the A C A C A rounds, the plausibility check, stretched arms, region memory, the two-generation settle, the fluid window, and the IOKit "disk busy" check.

3.5 Flags

  • --fixed freezes only the flying number; --max-stuck 0 takes away the stuck reads' room. Together, with --readers 4 --chunk 1M, they're rclone's shape (make demo-fixed).
  • --max-readers keeps its range (1 to 256); its default is now none (256 in effect).

4. Where the build departs from the request

  • Reads to slow files count as stuck from the start, not after 50 ms (3.1).
  • One read at a time for a file with no finished read, and at most flying + 16 open files: neither was in the request; both keep a newly met slow file, or many of them, from swallowing the flying reads.
  • The stuck cap can be passed for a moment (3.3), since a read can't be known to be stuck before it's sent. Nothing is canceled to get back under it; finished stuck reads just aren't replaced.

5. What was verified, and how

  • make test: go vet, then 55 tests with the race detector, all passing (the diagnostic is skipped by design). New or rewritten:
    • TestSlowFileGetsTheStuckRoom: a slow file (200 ms reads, served in parallel) and 16 fresh ones, 4 flying reads. With room for 16 stuck, the slow file had 16 reads at once and never more, and all 64 fresh chunks were done before the slow file was half done. With no room, the slow file had at most 4, and so did everything.
    • TestStuckReadsStopAtTheCap: every read 100 ms, 8 flying readers (as if the tuner had climbed in fresh data). At most 16 reads in flight, 16 counted stuck at once, and none left counted stuck after the run. Before the fix, the same case ran 24.
    • Tuner, in virtual time: climbs 4 at a time and stops at the knee (4 → 8 → 12 → 16, 20 not kept); no ceiling at 32 (a drive whose gains end at 40 goes to 40); stays when more doesn't help; rechecks step 16 → 12 → 8 when more starts to hurt; fixed never moves; starved holds, and starvation mid-test goes back; too few flying reads holds; steady under jitter; ops begun before a change don't count.
    • TestOrders (1 flying read, no stuck room) still copies in exact dfs and hash order.
  • The built binary on the demo tree (972 MB, 362 files, --simulate degraded --plain): done in 46 s, no errors, and diff -r against the source finds no difference.

6. Why the v2 tuner failed in hash order

It scored each candidate by throughput over trials of a second or two. In hash order the open files are a random mix of slow and fast ones, and in the simulator a slow read uses the drive's shared bandwidth at 8 MB/s against 500 MB/s for a fast one, so a trial's rate mostly reflected which files were open. Three things in the verdict then made it worse (probe/old-tuner-rule/ models them):

  • The plausibility check clipped the top. For doubled readers it voided any round reading above 2.3× or below 0.435×, a range centered on "no change". The true gain was 1.79×, so a reading 28% too high was thrown out while one 4.1× too low still counted, and the surviving rounds averaged low: 1.51× at a per-trial spread (sigma) of 0.3, 1.28× at 0.5.
  • Keeping was hard: more readers needed an average gain above the round's own measured noise and both halves positive. At sigma 0.5, 12% of 4 → 8 rounds kept, 19% rejected, 70% thrown out.
  • One rejection ended the climb, so the −10% was one ordinary unlucky round.

Measuring only flying reads removes the cause rather than the symptoms: no stuck read is in the measurement, so the file mix isn't either.

7. Concerns and open issues

7.1 The simulator can't show the two kinds of read helping each other

The simulated drive serves every read through one queue, so with 16 slow reads queued, a fast read waits behind them and counts as stuck too. That's why the diagnostic shows almost every read stuck and the tuner never finding enough flying reads to test. On that drive model it's harmless: the slow bandwidth is saturated with about 14 reads in flight, and 16 keeps it saturated. Showing fresh files flying past slow ones needs either a real drive whose slow reads don't block fast ones, or the simulator variant with separate slow and fast resources that v2 proposed. Neither exists yet. TestSlowFileGetsTheStuckRoom shows the engine side with sleeps standing in for the drive.

7.2 Is 16 the right cap?

It's a fixed bet, now a flag. If the real drive's slow regions keep speeding up past 16 reads at once, a higher --max-stuck would copy old data faster; if they don't, 16 already queues more than helps, and only costs a slower Ctrl-C and a slower return to fresh data. Only a run on the real drive (in a Thunderbolt enclosure) can say.

7.3 A log with home-folder paths (found during this work)

The first make tuner-diag run failed (the demo tree's path was relative, and go test runs in the package's folder), and the panic's stack trace printed absolute source paths, which include the home folder's name, into _logs/tuner-diag-20261013T051638Z.log. The session didn't edit or delete it (it's in ~/jorp). The cause is fixed: test targets build with -trimpath, so traces name files by module path, and the diagnostic passes an absolute path built from $PWD at run time.

7.4 Not yet done

  • No run on the real degraded drive. Whether its slow regions speed up with more reads in flight, and whether fast reads wait behind slow ones inside it, decide how much the room for 16 stuck reads buys.
